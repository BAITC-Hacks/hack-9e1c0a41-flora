## Кейс
Кейс 04 «Beeline Tariff Marketing Campaigns». Синтетическая база из 23 441 абонента. Агент (`agent.py`,
`class Agent`, метод `act(env)`) запускает пилотные кампании (`env.run_pilot`), получает шумный результат
и возвращает план из ≤10 кампаний: сегмент (фильтры `filter_arpu_segment` LOW/MID/HIGH,
`filter_data_segment` NON_USER/LITE/HEAVY, `filter_call_segment` LOW/MEDIUM/HIGH, `filter_current_tariff`
"tariff_4;tariff_8") → `target_tariff` (tariff_1…tariff_21) → `channel` (push 0 у.е. ×0.50, sms 4 у.е. ×0.65,
digital_ads 22 у.е. ×0.85, call 160 у.е. ×1.20).
Чистый результат = прирост ARPU по уникальным абонентам − затраты на контакты. Лимиты: бюджет 100 000 у.е.,
15 000 контактов, 20 пилотов по 10–200 абонентов, до 5 000 абонентов на кампанию. Пилоты шумные
(sd ≈ 0.80/√n). Судейская модель эффектов отличается от выданной истории.
Шаблон на мок-среде при seed 42 дал **−1 035 279**, повторно проверено при ревью 23.09.2026.
Это отдельный запуск, не универсальный результат шаблона. Бездействие имеет net=0; цель — положительный
результат на наборе проверок и улучшение относительно шаблона. На скрытой среде прибыль не гарантирована.

## Контракт с кодом Claude (под него пиши панель)
Согласуем с Claude до реализации. После `plan = agent.act(env)` у объекта агента есть:
- `agent.trace: list[dict]` — журнал решений по порядку. Поля:
  `step` (int), `phase` ("prior" | "pilot" | "decision"), `current_tariff` (str | None),
  `arpu_segment` (str | None), `target_tariff` (str | None), `channel` (str | None),
  `n` (int | None, фактический `res["n_customers"]`), `observed` (float | None, наблюдаемый ratio пилота),
  `post_mean` (float | None), `post_sd` (float | None), `note` (str, объяснение по-русски).
- `agent.plan_table: pandas.DataFrame` — итоговый план. Колонки: `campaign_name`, `filters` (str),
  `target_tariff`, `channel`, `n_customers` (int, оценка), `expected_net` (float), `lower_bound` (float),
  `reason` (str).
- `agent.explanation: str | None` — шаблонное объяснение. Дополнительный LLM-разбор вызывается
  из панели по запросу после расчёта; интерфейс `llm_explainer.py` отдельно согласовывается с Claude.

`post_mean` и `post_sd` относятся к ratio указанного в строке канала; при переводе оценки между
каналами переводится и sd. `expected_net` и `lower_bound` — оценки чистого результата финальной
кампании, не фактический скоринг и не доказанные гарантии. Их нельзя суммировать с пилотами без дедупликации.

Результат скоринга: `from local_eval import evaluate_agent`, затем
`result = evaluate_agent(agent, seed=seed, verbose=False)` → dict с ключами `net_arpu_gain`, `gross_arpu_lift`,
`total_cost`, `unique_customers_targeted`, `coverage_pct`, `roi`, `risk_score_pct`, `budget_used_pct`,
`n_pilots`, `n_campaigns`, `total_contacts`, `campaigns_detail` (список dict: `name`, `channel`, `cost`,
`n_contacts`, `gross_lift`, `n_negative`). Возможен `None`, если нет ни пилотов, ни финальных кампаний.
Внимание: `evaluate_agent` сам создаёт мок-среду и сам вызывает `agent.act(env)`, поэтому передавай ему
**новый** `Agent()`, а `trace`/`plan_table` читай с этого же объекта после вызова.

`n_campaigns` в результате включает пилоты: финальных кампаний `n_campaigns - n_pilots`.
`total_cost` и `total_contacts` уже включают финальные кампании; остатки в env после `act` учитывают
только проведённые пилоты. Не показывать эти остатки как остатки всего плана.
`gross_lift` по строкам `campaigns_detail` считается до дедупликации между кампаниями, поэтому сумма
строк может отличаться от итогового `gross_arpu_lift`. Итоговые метрики брать только из result.
Скорер перехватывает исключения `act`: наличие result само по себе не доказывает успешность агента.
Показывать отсутствие финального плана как проблему, не как удачное завершение.

## Задачи по приоритету

### Задача 1 — `app.py` после назначения разработки капитаном
Запуск: `streamlit run app.py`. Работает из корня репозитория.
- Боковая панель: целочисленный seed от 0 до `2**32 - 1`, по умолчанию 42, кнопка «Запустить агента».
- Сверху метрики из реального result: чистый прирост относительно бездействия (0), затраты, уникальный
  охват, пилотов из 20; компактно показать контакты из 15 000 и число финальных кампаний из 10.
  ROI показывать только при затратах >0, иначе «не определён».
- Сравнение с шаблоном только на одинаковом seed: результат вычислить тем же evaluator для
  `agent_template.Agent`. Число -1 035 279 допустимо как явно подписанный справочный запуск seed 42,
  его нельзя использовать как baseline для всех seed. Сравнение вторично относительно основного запуска.
- Блок «Разведка»: таблица реально проведённых пилотов и решений. Показывать реальные причины,
  не утверждать, что гипотеза точно убыточна, только по шумному наблюдению.
- Блок «План»: `plan_table`, в том числе `reason`, прогноз отдельно от оценённого средой результата.
- Блок «Объяснение»: `agent.explanation` или понятное сообщение об отсутствии объяснения.
- Если у агента ещё нет `trace` или `plan_table`, используй `getattr(..., None)` и покажи понятную заглушку, а не падай.
- Пока агент не готов, пустое состояние достаточно. При необходимости разработки интерфейса можно
  включить `DEMO_STUB=1`, но с явной маркировкой «Тестовые данные интерфейса» и без сравнений/заявлений
  о результатах. В сдаче и демонстрации основного сценария этот режим выключен.
- Выполнение только по кнопке; сохранить результат в session_state с seed и идентификатором версии,
  не перезапускать агента из-за обычной перерисовки страницы. Исключения и пустой результат обработать явно.

После готового основного сценария, при запасе времени:
- График: точки `observed` отдельно от линии `post_mean` и интервала `post_mean ± 2*post_sd`.
  Интервал относится к оценке модели, не к точке наблюдения и не гарантирует прибыль.
- Столбики кампаний из `campaigns_detail` с отдельными пилотами и финальным планом; подпись про дедупликацию.
- Вкладка «Устойчивость»: seed 0–9, LLM выключен; кэш включает seed, версию агента и данных,
  сохраняет результаты/таблицы, не объект Agent. Основные проверки устойчивости остаются в CLI.

Результат: `app.py`; добавление streamlit в зависимости координировать с Claude, который интегрирует проект.
